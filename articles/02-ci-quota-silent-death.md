# GitHub Actions 超额 597 分钟后，我的 CI 静默死掉了——而没人发现

> 事故日期：2026-07。最危险的失败不是报错，是**你以为它在跑**。

## 事故经过

GitHub Actions 免费额度 2000 分钟/月。2026 年 7 月，我的账号实际用了 2597 分钟。

超额之后发生了什么？什么都没发生——这正是问题所在。没有邮件、没有报错、没有红色的 X。push 之后 Actions 干脆不跑了，PR 页面上检查那一栏安安静静。如果你习惯了"没看到红的就是好的"，未验证的代码就会一路绿灯上生产。

我算是幸运的：是在对账的时候主动发现额度超了，而不是在某次线上事故后回溯发现的。但我意识到这个失败的形态极其恶劣——**CI 的死亡是静默的，而静默的死亡会被默认为健康**。

## 反思：额度应该是一个显式变量

复盘时我总结出一个更普适的原则：**任何"耗尽即静默失效"的资源，都必须变成流程里可见、可自动绕过的变量。**

CI 额度恰好是这种资源。而对中国开发者来说，它不是唯一的：

- 本机性能有限，全量测试/构建跑不动（Mac 上还要避开 Docker）
- 自建构建机（NAS、软路由、家庭服务器）连通不稳定
- 拉境外 Docker 镜像慢或失败
- 代理工具抢路由，ssh 走错网卡

这些问题的共同解法是同一句话：**把"在哪验证"从隐含假设变成显式的、自动降级的、留证据的路由决策。**

## 落地方案：构建门禁三级路由 + 欠账补验

我写了一个 `build-gate.sh`，所有仓库的验证统一走它：

```
1. CLOUD   GitHub Actions —— 额度充足时的默认路径
2. BUILDER 专用构建机     —— 额度不足/查不到时自动降级（amd64 + 干净环境）
3. LOCAL   本机兜底       —— 构建机也不可达时；证据最弱，会被明确标注
```

关键设计有三点：

**1. 额度查不到 = 按不足处理。** 查询失败时保守降级，绝不默认"应该还有额度"。

**2. 三条路跑同一条命令、写同一份证据。** 结果追加进仓库里的 `docs/BUILD-EVIDENCE.md`：commit SHA、走的哪条路和为什么、额度快照、门禁命令、结果。任何人、任何 agent 都能查到"这个 commit 到底被谁、在哪、用什么命令验证过"。换 agent 不丢上下文。

**3. 本机兜底通过 ≠ 结案，只是欠账。** LOCAL 通过的记录进一个队列，cron 每 15 分钟探测构建机——恢复了就自动用 `--force-builder` 复验，通过销账，失败保留。**欠账未销的 commit 禁止发布。** 这条是最重要的：降级不能降标准，弱证据必须可还清。

## 效果

现在每次门禁输出长这样，路由决策完全透明：

```
════════════════════════════════════════════
 构建门禁 · myapp @ 910312a6 (main)
 CI 额度剩余约 1673 min（保留线 200）
 路由：LOCAL —— 构建机不可达，降级本机
════════════════════════════════════════════
  ⏳ 已记入补验队列 —— 构建机恢复后自动复验此 commit
```

## 代码在这里

整套模板（`build-gate.sh` + `reverify.sh` + README）开源在 VibeDevOps skill 里，bash 3.2 兼容，macOS 自带 bash 直接跑：

- 模板：https://github.com/iPythoning/VibeDevOps-skill/tree/main/skills/vibedevops/templates/build-gate
- 顺带一个坑：macOS 的 bash 3.2 下 `$VAR` 紧跟全角字符（；，：（））会被吞进变量名，`set -u` 时直接报 unbound variable——shell 里变量后接中文一律写 `${VAR}`。这个坑 `bash -n` 查不出来，只能冒烟测出来。
