# 绿色的谎言：一天之内，我的三道门禁都在骗我

> 事故日期：2026-08。一条 CI/CD 链路被「修好」了一周，每次都有绿色证据。
> 真相是：**验证时走的那条路，和生产实际走的那条路，从来不是同一条。**

## 一、"跑通了"——但跑的是另一条路

那条流水线的结构很常见：一个**构建工作流**负责出镜像，一个**部署工作流**调用它、
然后把镜像送上生产。构建工作流同时开了「手工触发」，方便单独验证。

一周里我反复"修好"它，每次都手工触发构建工作流，绿。合并到主干，红。再修，再手工验，
再绿，再合并，再红。

直到我去读那次失败的日志，看到了这个：

```
env:
  SSH_PRIVATE_KEY:        ← 空
  SSH_HOST:               ← 空
  SSH_USER:               ← 空
  REGISTRY_TOKEN: ***     ← 有值（平台自动注入的那个）
```

**可复用工作流不会自动继承调用方的 secrets。** 只有平台自动注入的那个令牌有值，
其余全是空字符串。而**手工触发时，仓库 secrets 是可用的**——所以单独测那条路永远绿。

更恶劣的是它失败的样子：空的主机名传给一条 `ssh-keyscan`，那条命令的 stderr 被
`2>/dev/null` 吞掉，`set -e` 让整步静默退出。**日志里一行输出都没有，只有一个退出码 1。**

三件事叠在一起，才让这个坑活了一周：
1. 可复用工作流的 secrets 默认不继承，且缺失表现为**空字符串而不是报错**；
2. 手工触发这条岔路，**形状与生产不同**，却被当成等价验证；
3. `2>/dev/null` 把唯一的线索吞了。

## 二、"验过了"——但验的是还装着它的那个产物

同一天，我在给一个镜像瘦身。有个依赖占了可观体积，查过生产数据确认那个功能从未启用，
于是把它改成可选依赖。构建、跑冒烟、全绿、合并、部署。

**应用启动即崩，公网 502。**

原因是这一行：

```python
def _make_handler(self, ...) -> sdk.EventDispatcherHandler:
```

文件顶部有标准的守卫写法：`try: import X except ImportError: X = None`。它挡得住**运行时**
使用，但**挡不住导入期求值的类型注解**——函数签名在类定义时就会求值，`None.Attr` 直接抛异常。

而我为什么没测出来？因为我的冒烟跑在**上一版镜像**上，**那个镜像里依赖还在**。
真正卸掉它的产物，我一次都没验过。

> **删掉一个依赖之后，验证必须在真正没有它的产物上进行，而且要复现完整启动链，
> 不是跑一遍 `import`。** 在仍装着它的镜像上做的验证，等于没做。

## 三、"它一直是红的，已知问题"——它从来没扫过

第三道门禁是密钥扫描。它红了几十次，团队里所有人都知道"那个是假红，忽略就行"。

去读日志才发现，它红的原因是扫描器**自己**在调用一个外部 API 判断账号类型，
而那次调用在代理环境下失败了，于是扫描器落进了「需要付费授权」的分支。

**也就是说：过去每一次「密钥扫描失败」都不是扫描结果。这道门禁从没扫过一次密钥。**

而它长得跟"扫到了"一模一样，没有任何人能从界面上分辨。

## 反思：三件事是同一个形状

它们看起来是三个独立的 bug，其实是同一个结构性缺陷：

> **绿色/红色信号，与它声称代表的事实之间，没有任何机制保证对应关系。**

- 第一件：绿色代表"手工路径能跑"，被读成"生产路径能跑"
- 第二件：绿色代表"旧产物能启动"，被读成"新产物能启动"
- 第三件：红色代表"扫描器自己坏了"，被读成"扫描器在工作"

**一道从未失败过的门禁，和一道不存在的门禁，在证据上无法区分。**

## 落地：四条可以照抄的规矩

**① 门禁必须先证明自己会失败，再去做真正的检查。**

密钥扫描现在的第一步，是在临时目录里**现造一个随机的假凭据**让扫描器去扫。
扫不出来就让这一步红，并明说「本次『扫描通过』不可信」。

随机生成是刻意的：写死的样本会进仓库、会被下一步自己扫到，也会随时间变成真的可疑内容。

同样的做法适用于回滚逻辑——**回滚路径必须在平时就走过一次，不能等出事时第一次用。**

**② 跳过不是通过。**

把守卫写成 job 级 `if:` 条件时，不满足条件的行为是**跳过**，而**跳过的工作流在界面上是绿的**。
于是「拒绝部署」和「部署成功」长得一样。

拦截必须是**显式失败**：非零退出 + 明确错误行，放在第一个 job 的第一步，
让下游依赖自然阻断。

**③ 岔路要删掉，不是规范。**

与其规定「测试要走生产同款路径」，不如把不同形状的入口删掉：构建工作流只保留
「被部署工作流调用」这一种触发方式。

代价要说清楚：不能「只构建不部署」了。补偿方式是把**「构建但不推送」加进 PR 门禁**——
它与生产同形，不会造出第二条假路。

顺带堵一个洞：手工部署入口默认**可对任意分支生效**，不加分支守卫就等于
「任意分支都能部署到生产」。这个洞在我扫描的四个仓库里，**全部开着**。

**④ 不要吞 stderr。**

`cmd 2>/dev/null` 配合 `set -e`，会把「为什么失败」连同失败一起吞掉。
这次事故里，一条被重定向的命令让整个部署步骤零输出退出。

讽刺的是，我在修完这条之后的同一个下午，自己写了一句
`git push --quiet 2>/dev/null`——四个仓库的推送**全部失败**，而我看到的是空输出，
差点当成成功。

## 最后一句

这套东西最贵的不是宕机，是**信任**。

假门禁比没有门禁更危险：没有门禁时你知道自己在裸奔，会小心；
有一道假门禁时你以为有人在把关，于是不再看。

所以现在验收一道门禁的标准，不再是「它绿了」，而是——

**它证明过自己会红吗？**
