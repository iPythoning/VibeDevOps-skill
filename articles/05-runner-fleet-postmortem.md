# 一次 EmDash 升级，引爆了我三个月埋下的 9 颗雷

> 复盘区间：2026-07 ~ 2026-09。一次平平无奇的「跟随上游版本升级」，把自建 runner 车队三个月积累的静默损伤全部引爆。本文按雷区复盘每一颗雷：**现象 → 根因 → 为什么之前没爆**，以及最终把系统从「反复施工」变成「已竣工」的处方。
>
> 机器坐标已脱敏：hk-builder = 香港 4C/8G 按需构建机；xserver = 大陆 16C/46G 常驻构建机；生产机 = 部署目标。它们的真实身份不重要，雷的模型是通用的。

## 背景：三个月「建好了」的基建

故事起点和许多 vibe coder 一样：GitHub Actions 免费额度耗尽（见 [02：额度静默死亡](02-ci-quota-silent-death.md)），于是把 CI 迁到自建 runner：一台香港小机跑按需（on-demand）runner，一台大陆大机跑常驻 runner，Mac 做暖缓存兜底。9 月的一次 EmDash 平台升级，触发了一串真实的构建/部署 job——然后一切开始连环爆炸。

**升级本身没有制造任何问题。升级只是把真实流量第一次打进了带伤的管道。** 平时系统看起来是绿的，因为 job 没来过；洪流一到，每个暗伤按顺序发作。以下是挖出来的 9 颗雷。

## 雷区一：「完成了」的迁移，16 个仓实际无 runner 可调度

**现象**：升级触发某仓 CI，job 排队 30 分钟无人接。

**根因**：迁移时给 19 个仓都设置了路由变量 `CI_RUNNER=["self-hosted","hk-build"]，但只有 8 个仓被按需控制器盯梢；其余 11 个仓的 hk-build 标签**没有任何在线 runner 匹配**——旧常驻注册早已离线，控制器又不看它们。这不是边角案例：清单上 19 个仓有 16 个处于「下次 push 永久排队」状态。

**为什么之前没爆**：这些仓自迁移后没触发过 CI。job 从没来过，排队就不存在。

**处方**：把 16 个仓逐个补进控制器的盯梢清单（带热加载，无需重启），然后 push 实测立即被接走。**「配置写完了」≠「路径走通过」——每一条路由都必须用一个真实 job 验证过才算数。**

## 雷区二：按需控制器的静默拒收

**现象**：一个仓的 job 永远排队，控制器健康表里只显示一个模糊的 `identity`，没有任何解释。

**根因**（两颗叠加）：
1. 控制器按设计**只服务私有仓**（`validate_repo` 硬校验 `private is True`）——这是正确的安全设计（自建 runner 跑公有仓 = 任何 fork PR 都能在你的机器上执行代码），但拒收时把原因塌缩成 `identity`，排障时完全看不出是「公有仓被设计拒收」。
2. 仓名**大小写敏感**的身份校验：`VibeDevOps-skill` 配置成 `vibedevops-skill` 即被拒收。

**为什么之前没爆**：被拒的 4 个仓恰好也不在另外的车道上活跃，静悄悄的。

**处方**：4 个公有仓移出控制器清单，路由改到大陆常驻机车道。**教训有两条：安全设计要配可读的错误（`public repo refused by design` 而不是 `identity`）；往任何带身份校验的系统里登记名字，必须原样复制 API 返回的大小写。**

## 雷区三：假 watcher 与僵尸注册

**现象**：服务器上跑着一个看似关键的 `hk-runner-watcher` 服务，19 个仓的 runner 注册列表里躺着一堆 offline 的 `hk-builder-<repo>`。

**根因**：watcher 脚本是个**循环体为空的 no-op**（`for repo in ; do` 什么都不执行）——上一任迁移留下的躯壳；那些 offline 注册是更早一代的常驻 runner 尸体，标签还带着 `xserver`、`build`，与在线的新 runner **标签重叠**：任何写死 `[self-hosted, xserver]` 的 workflow 都会在两台机器间随机分裂调度。

**处方**：disable 假服务，批量删除 20 个僵尸注册（全 offline，删除零风险）。**标签重叠必须从根上消除——靠「记住别这么写」不行，要让旧标签的宿主消失。**

## 雷区四：明文 token 与共享命运的限流饥荒

**现象**：某天控制器开始「集体眼瞎」——所有仓的扫描报 `api_backoff`，job 全部排队，控制器自己的日志显示配置校验循环失败。

**根因**（两层）：
1. 历史包袱：旧 watcher 脚本里躺着一枚明文 `gho_` PAT（已按泄露处理：吊销换新）。
2. **三四个服务（hk 控制器、xserver 控制器、fleet 路由器、探针）共用一枚 fine-grained token**。GitHub 的 rate limit 是按 token 计的，任何一个食客暴食，全桌断粮。当天的直接死因就是共享额度被榨干、API 对控制器拒绝响应——它不是「不想接活」，是「瞎了」。

**处方**：三桶分账（hk 控制器 / fleet / xserver 控制器各一枚，15,000 次/小时 ×3）；外加一个此前没有的发现——控制器有个「fleet API 预算守护」，额度低时会动态要求更大的扫描间隔，共享桶时代它隔三差五把整个调度器冻成只读。

**为什么之前没爆**：额度充裕时谁也没发现食客之间的关系；一次脉冲式消耗把共享桶打穿，耦合才显形。

## 雷区五：worker「接活即死」——一个 mkdir 的代价

**现象**：给大陆大机部署第二个按需控制器（10 build + 2 control 槽），注册 ✓、抢单 ✓、置备 ✓，但 job 一上手就死：**0 个 step、无日志**，三次干净复现一致。

**根因**：runner 的 systemd 单元模板里硬编码了 `RUNNER_TOOL_CACHE=/opt/hostedtoolcache` 和 `npm_config_cache=/opt/build-cache/npm`。小机上这两个目录在装机早期就建好且是 runner 用户属主；大机是新装的，**目录不存在**。worker 一起步要写工具缓存 → 目录不存在、runner 用户无权在 `/opt` 下自建 → 瞬间崩溃。更阴的是：崩溃发生在 step 执行前，所以 0 step 无日志；控制器跑完即清理 slot 目录，**证据随尸体一起火化**——前三轮排查一直在抓瞎。

**确诊方法**：把 runner 手动拉起来（root 直跑 `run.sh --once`，绕开单元环境变量），它活了——delta 只剩单元环境；逐一比对发现缺目录。

**处方**：两个 `mkdir -p` + chown。修复后 4/4 实测全绿。**教训：①新装机 checklist 必须包含「控制器声明的所有缓存目录存在且 runner 用户可写」；②诊断「启动即死且无日志」的进程，第一招是绕开它的启动环境（systemd 单元、容器、wrapper）手动复现——delta 就是嫌疑人。**

## 雷区六：34G 尸体与 96% 的磁盘

**现象**：构建机磁盘 96%，docker 本体只占 22G——**另外 50G 找不到主人**。

**根因**：`/home/runner` 34G——旧常驻 runner 时代的工作目录， runner 死了目录没死；外加 2.7G 死代码系统的状态目录。docker 镜像数据在 containerd 存储（`/var/lib/containerd`），不在直觉的 `/var/lib/docker`，第一轮 du 差点把方向带偏。

**处方**：验证零进程零单元引用 → 改名观察 → 删除；装每日 prune 定时器（72h 未用镜像 + 48h 构建缓存，**在跑与近期制品受保护**）；磁盘 96% → 50%。

**为什么之前没爆**：磁盘满之前，一切都是免费午餐。

## 雷区七：多智能体互踩——没有锁的并发写入

**现象**：凭据文件在无人操作的情况下反复消失又出现；另一个时段，配置在「没人承认改过」的情况下变化。

**根因**：本机同时跑着八九个智能体，**共用同一把 root SSH 钥匙进同一批机器**，没有锁、没有归属、没有审计。一个领了「凭据清理」任务的 agent 把新 token 当泄漏删了；两个 agent 同时改同一份 JSON，后写覆盖先写。

**处方**（这才是治本的那味药）：
- 服务器装 `infra-write-lock`（flock 互斥 + 强制留痕审计日志），写基建前必须持锁、必须报身份；
- 全局 `AGENTS.md` 加铁律：同一机器同一时刻只允许一个写入者，只读探查不受限；
- 明确归属：机道配置归一个会话，其他 agent 只读。

**为什么之前没爆**：迁移期写入时间错开了。撞车只需要两次写入落在同一个五分钟窗口里——今天撞了两次。

## 雷区八：胖镜像——dev 依赖跟着上生产

**现象**：一个 EmDash 站点的镜像 2.45G。

**根因**：验尸（`docker history`）只有一层凶手：构建把**完整 node_modules（含全部 devDependencies）**拷进运行镜像。这是平台构建模板的问题，不是站点仓的问题——所以修一次，全平台受益。

**处方**：多阶段构建 / `npm prune --omit=dev`，预期 2.45G → ~500M。基础镜像 pin digest + Renovate 跟踪（可变 tag 上游打安全补丁时，Dockerfile 文本不变、层缓存不会自动更新——要么 pin digest 靠 Renovate 提 PR，要么每周 `--pull` 刷新一次，二者都做）。

## 雷区九：验收基于「声明」，而不是「证据」

**根因（压轴）**：以上八颗雷能埋三个月，共同的原因是**验收方式**——迁移完成与否，看的是「配置写了、文档写了」，不是「每个关键 job 的真实 runner_name 是什么、每个标签有没有在线宿主、每条缓存路径存在吗」。后来用不信任式验收（假设撒谎、逐项命令取证、红队找反例）重新审，一次抓出 5 处文档与现实的偏差、2 处高危漏检。

**处方**：验收永远问三个问题——**每个关键 job 实际跑在哪台机器（runner_name）？它依赖的每条路径/每个标签/每枚 token 此刻存在且匹配吗？反例搜索找到了什么？**「runner online」不构成证据：online 的 runner 可能不接你的 job，接你 job 的 runner 可能马上死。

## 总结：一张自检清单

如果你是自建 runner 车队（或在 vibe coding 中让 AI 管基建），开机自检这 10 条，每条都要能用命令回答「是」：

1. 每个路由变量指向的标签，此刻有没有在线 runner 匹配？（`gh api .../actions/runners`）
2. 每个仓的最近一次 CI/CD，真实 runner_name 符合预期车道吗？（jobs API）
3. 控制器/路由器的覆盖清单 = 你以为的清单吗？（读回配置，别读文档）
4. 公有仓和私有仓分车道了吗？身份校验的错误信息读得懂吗？
5. 旧注册/旧服务/旧目录清了吗？标签有重叠吗？
6. 几个服务共用一枚 token？rate limit 撞线时谁会一起瞎？
7. runner 声明的每个缓存目录存在且属主正确吗？（新装机必查）
8. 磁盘里最大的 5 个目录都是什么？有每日保洁吗？
9. 多少 agent 能写这台机器？有互斥锁和审计日志吗？此刻谁在持锁？
10. 验收报告里的每条「已完成」，对应的命令证据在哪？
