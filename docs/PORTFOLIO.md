# Making CI/CD safe for coding agents — a work sample

*Platform / DevEx / agent-infrastructure.* GitHub: **[@iPythoning](https://github.com/iPythoning)** · Contact: `<your-email>` · `<your-linkedin>`

When 40–70% of a team's pull requests are written by coding agents, one question has no good answer yet: **what may an agent merge on its own, and how do you know the checks that approve it are real?** Everything below is my answer, and it has a single shape — *a gate must prove it can fail, and a decision must be mechanically enforced, not remembered.* Every claim links to running code and green CI in this repo.

The signal I'm trying to show is not "I can write a CI pipeline." It's two things that don't come out in an interview and can't be generated by an LLM: **reasoning at the level of evidence, and knowing when my own criteria lie to me.**

---

## 1. A gate must prove it can fail before it's allowed to pass

> A gate that has never failed is indistinguishable from a gate that does not exist. — [ADR 0009](adr/0009-gates-must-prove-themselves.md)

A secret scanner that's been "red for weeks, known issue" may never have scanned anything — it can fail for its *own* reasons and look exactly like "found a leak." So the scanner's first step now mints a **randomly generated** fake credential in a temp dir and scans *that*; if it isn't caught, the step goes red and says, in words, that this run's "scan passed" is not trustworthy. Randomness is deliberate: a hardcoded sample lands in the repo and gets flagged by the real scan.

- **Code:** the canary step in [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) (`secrets` job) and the shipped template [`pr-check.yml`](../skills/vibedevops/templates/ci/pr-check.yml).
- **Receipt:** on `main`, the `Gate self-proof — gitleaks canary` step is **green** — it downloaded the same gitleaks, planted a random `ghp_` token, and confirmed the scanner catches it. (I found the AWS-key form of this canary *silently didn't detect* under a local test and switched patterns before shipping — a canary you haven't run is itself a fake gate.)

## 2. Merge authority is gated on reversibility, not on a green checkmark

> What gets automated is *confirming the change works* — never *carrying the irreversible consequence for a human.* — [ADR 0011](adr/0011-verification-autonomy.md)

Auto-merge tools gate on "checks are green"; dependency bots gate on "patch vs minor." Neither asks the question that actually matters: **if this change is wrong, can it be undone automatically?** Changes are scored on reversibility × evidence into three tiers; anything touching migrations, `.env`, or secrets is T3 — never delegated, no exceptions.

- **Code:** [`automerge-tiers.sh`](../skills/vibedevops/templates/ci/automerge-tiers.sh). It refuses to even score a repo whose `main` has no branch protection — "putting a smart lock on a house with no door."

## 3. A judge that knows it can be fooled

This is the part I'd most want a reviewer to read. The precondition check above had to answer "does this branch have protection?" — and getting *that judgment* right took three tries, each documented in the code where it lives:

```bash
# The criterion cannot be "empty output means unprotected" — gh api on a 404 prints the
# error JSON to *stdout* (a real 149-byte {"message":"Branch not protected",...}), so that
# criterion is always false and the gate silently fails open. Check a substantive field.
#
# And take .url, not some boolean: jq's `//` treats *false and null identically*, so
# `.required_status_checks.strict // empty` judges a normal protection with strict=false
# as "unprotected" (hit this myself — same failure mode, third time).
PROT=$(gh api "repos/$REPO/branches/main/protection" --jq '.url // empty' ...)
```

Two ways for the *judge itself* to be wrong — a scanner writing its error to the channel you read as the result, and a JSON operator that can't tell `false` from `absent` — both caught only because I'd been burned before and now write the criterion to survive it. That "my own criterion will lie to me" reflex is the single hardest thing here to fake, and it generalizes far past this one check.

## The move that ties it together: a rule is not a mechanism

I wrote gate-self-proof down as a formal decision — and then didn't implement it for weeks. I hardcoded a hosted runner in my own CI while a doc I'd authored told everyone else not to; I left the `--if-present` silent-skip in the very template that preached against it. I only found out by running an **8-agent adversarial audit of my own repo** and getting the receipts.

So I built the enforcement one level up ([ADR 0012](adr/0012-adr-decisions-must-be-mechanically-reconciled.md), [`check-adr-compliance.sh`](../skills/vibedevops/scripts/check-adr-compliance.sh)): a checker that runs every stated invariant in CI **and fails the build if any decision has neither an executable check nor an explicit exemption** — you can't add a rule and forget to enforce it, because forgetting is now a red build. The checker is guarded by mutation tests, so the judge can't quietly rot. The narrative version is the essay [*Green Lies*](../articles/04-green-lies-fake-gates.en.md).
