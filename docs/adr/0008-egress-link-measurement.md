# ADR 0008：出境链路必须分域分方向实测——「能连」≠「能传」

- 状态：Accepted
- 日期：2026-08-19
- 补充：ADR 0005（大陆容器构建）、0006（变量路由）、0007（自治路由与网络自适应）

## 背景

0005–0007 解决了「构建可复现」「调度不受配额影响」「路由自动适应」。但它们共同预设了
一件没被验证的事：**只要探测到「通」，这条路就能用。** 探测用的是 `curl` 打一个
端点看状态码与握手耗时。

一次真实排障推翻了这个预设。现场是「构建机在大陆家宽、生产机在境外、制品仓在境外」
的常见拓扑，症状是「能构建、送不出去」。

## 决策

### 一、可达性必须分「域」和「方向」两个维度实测，握手不算数

同一个大文件、同一时刻、两条出境路的实测：

| 路径 | 下行 | 上行（50MB PUT） |
|---|---|---|
| 商业代理 | 62 Mbps | **3.8 Mbps，且中途 HTTP 000 断连** |
| 自有同城云主机隧道 | **0.41 Mbps** | — |
| 对照：同一台云主机 → 境外生产机 | **320 Mbps** | — |

**同一台云主机，到境外生产机 320 Mbps，到代码托管平台 0.41 Mbps。**
限速是**按目标域**施加的，不是按国界。「出国慢」是错误的心智模型。

因此规定：
- **握手可达性（状态码 + `time_total`）只能用于判断「是否被阻断」，不得用于选型。**
  握手与吞吐可相差两个数量级。
- **registry / 制品仓选型必须用 ≥100MB 真实镜像实测推与拉，且分别记录。**
- **上行与下行分别测。** 下行 62 Mbps 不代表上行可用——实测上行差 16 倍且不稳定。

### 二、代理生效范围要逐层验证，"配了" ≠ "生效"

一次排障中，同一台机器上代理在四层的表现互不相同：

| 层 | 表现 |
|---|---|
| 宿主 shell | 认 `HTTPS_PROXY`，正常 |
| 容器引擎守护进程 | **不认**——其代理配置项不在信号重载范围，需重启进程；而生产机上有大量在跑容器，不能随意重启 |
| BuildKit 守护进程 | **不认**——即便注入 `network=host` 与大小写四种 proxy 变量，registry 取 token 仍直连失败 |
| 构建容器内的 `RUN` | 取决于构建网络模式；平台若无默认网桥则**完全无网** |

因此规定：
- **"代理已配置"必须逐层实证**，至少覆盖：宿主命令、镜像推送、镜像拉取、构建期 `RUN`。
- **优先选用户态工具完成出网动作**（自己发 HTTPS、认标准 proxy 变量），不要依赖守护进程的代理支持。
- 平台无默认网桥时，构建须显式指定宿主网络模式；该配置应由变量注入，不写死。

### 三、`NO_PROXY` 是最容易自伤的一处，且必须改生成器

现场发现被墙域名被写进了 `NO_PROXY`——等于明令「访问它不要走代理」，而它直连不通，
于是必然失败。此坑此前"修过一次"，但只改了机器上的文件、**没改生成该文件的脚本**，
于是每次路由变化被重新写回。

因此规定：
- **`NO_PROXY` 只放确定直连可达的目标**；任何被阻断的域名进入 `NO_PROXY` 视为故障。
- **配置由脚本生成的，修复必须落在生成器**；只改产物 = 未修复。
- 加机器可验证的守卫断言，且**守卫本身要做反向验证**（构造违例确认它会红）。

### 四、自适应脚本的"撤销分支"是炸弹：可用性判据必须与探测目标解耦

网络自适应脚本的典型写法是：探测某个代表性端点，通则判定"直连恢复"并**撤掉代理配置**。

这在多域限速的现实下是错的：**代表性端点恢复 ≠ 所有目标恢复。**
现场即为：探测端点恢复直连后脚本会删除代理配置，而制品仓仍然直连不通
→ 推送链路在「网络变好」的那一刻全线失效。

因此规定：
- **代理配置的存废，判据是「代理本身是否可用」，不是「探测目标是否直连可达」。**
  探测结果只用于调整偏好（例如某些工具走不走代理），不得用于撤销出网能力。
- 撤销类分支必须做**双向变异验证**：构造「探测目标恢复」确认配置**不被删**；
  构造「代理真失效」确认配置**确实被删**（否则守卫是空转）。

### 五、跨境推送大 blob 必须分块

整块 PUT 大层在长肥且不稳的链路上会 `unexpected EOF`。分块（4MB 量级）+ 重试可扛住
中途断连：现场 884MB 镜像整块推必失败，分块后 669s 推成并回读到 digest。

### 六、镜像体积是跨境 CD 的一等公民指标

在实测有效 10.6 Mbps 的出境链路上，**每 100MB ≈ 75 秒发版时间**。因此：
- **镜像瘦身属于 CD 可用性工作，不是优化项。**
- 优先级：删「从来跑不起来的依赖」＞ 删构建产物（字节码缓存、包内测试）＞ 拆可选依赖。
- **删任何依赖前必须查生产实态**（该功能是否有数据、是否曾成功启用），不能只看代码引用。
- 已知无效的尝试：对 wheel 分发的 `.so` 做 strip（出厂已 strip，收益为 0）。

### 七、推送步必须带服务端回读断言

「推送命令退出码为 0」不等于「制品在仓里」。推送后必须回读 manifest digest 与架构，
不符即让该步失败——**不把没推上去的当成功**。

## 成熟度阶梯（自评基准）

**L0 不可接受**：制品只存在于某台机器；无 CI 门禁；密钥进过仓库。

**L1 最低标准**（低于此不应承接生产流量）
- 代码有远程副本；`.gitignore` 覆盖密钥；历史无密钥
- PR 门禁：密钥扫描 + 静态检查 + 测试 + 构建，全绿才可合并
- 制品不可变、tag = commit SHA；生产按 tag/digest 部署，可翻上一版回滚
- 生产机只拉已验证制品，**不在生产机构建**
- 部署后有健康检查，失败自动回滚

**L2 可持续**（本 ADR 的目标线）
- 构建车道≥2 且可零代码切换（ADR 0006）；路由自动适应（ADR 0007）
- 出境链路**分域分方向实测**并记录在案（本 ADR 一、二）
- 推送带服务端回读断言（本 ADR 七）
- 镜像体积纳入监控（本 ADR 六）
- 依赖显式声明——直接 `import` 的包必须在依赖清单里，不靠传递依赖苟活

**L3 成熟**
- 制品来源可证明：provenance / SBOM / 签名，部署按 digest 而非 tag
- CI 使用短期身份（OIDC）而非长期令牌
- 渐进式发布（canary / 蓝绿）+ 基于业务指标的自动回滚
- 构建可复现：同 commit 同 digest
- 制品仓与构建机、生产机的**网络距离**都经实测优化，不跨越已知限速域

**L4 最高标准**
- 任一车道、任一区域、任一供应商失效均不阻断发布（多活）
- 变更从合并到生产全链路可审计，含制品指纹与回滚证据
- 依赖与基础镜像有自动化更新与安全响应流程
- 成本与时延有预算并被持续验证

## 结果

- 排障顺序固定为：**分域测阻断 → 分方向测吞吐 → 逐层验证代理生效 → 才谈选型。**
- 禁止用握手延迟做选型论据。
- 撤销类自适应分支一律要求双向变异验证。
- 镜像体积进入 CD 健康指标。
