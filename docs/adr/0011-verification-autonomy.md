# ADR 0011：验证闭环必须自治——人是 verifier 就是并行度上限

- 状态：Accepted
- 日期：2026-08-27
- 关联：ADR 0009（门禁必须自证有效）、0006/0007/0010（交付管道自治三部曲）

## 背景：前十个 ADR 有一个共同的隐含前提

0006 变量路由、0007 无人值守 failover、0008 链路分域实测、0010 仓库接入对账——
这条线解决的是同一个问题：**怎么把代码安全地送上生产**。到 v1.6.0，这条管道
已经基本无人值守：新仓自动接入、账单故障自动切车道、构建失败自动回滚。

但它们共享一个从未被写下来的前提：**验证由人做**。

管道把制品送到生产，然后停在那里。「送上去的东西是不是对的」这一问，
每一次都要人接手。而这一问才是真正的工作量。

## 证据：把最近的真实故障按「谁完成了验证」重新归类

| 事件 | 门禁状态 | 谁发现真相 | 怎么发现的 |
|---|---|---|---|
| CD 切自建车道首跑红 | CI 全绿 | 人 | 读 384 秒的构建日志，发现 `network:` 参数在 workflow 里根本不存在 |
| 容器引擎卡死、磁盘满 | 无门禁覆盖 | 人 | 翻 supervisor.log 发现进程在等一个 GUI 错误对话框 |
| 可选依赖导致启动即崩 | 门禁全绿 | 人 | 生产 502 后回读源码，发现类型注解在**导入期**求值 |
| 每一次生产部署 | 部署 job 绿 | 人 | 手敲 `curl` × 3 + 看容器 healthy |

四行里有三行是「门禁绿着，而真相在别处」。ADR 0009 已经处理了其中一类
（门禁自己是假的），但它处理不了另一类：**门禁根本看不到的东西**——
界面是不是真的能点、这次改动有没有让首屏慢一倍、截图里那个错位来自哪个组件。

这类事实只能通过**实际操作产品**获得。而在 v1.6.0 的工作流里，
有能力实际操作产品的只有一个角色：人。

## 论点：门禁的边际收益在递减，验证能力的边际收益在递增

再加一道门禁，收益是「多拦住一类已知错误」——而已知错误正在被前十个 ADR
逐个吃掉，剩下的越来越薄。

给 agent 一次验证能力，收益是「它能自己确认任意一次改动是否成立」——
**这个能力对每一个后续任务都复用，而且可以并行**。N 个 agent 同时验证 N 个改动，
人只有一个，永远串行。

所以瓶颈的性质不是「质量不够」，是**并行度**。人做 verifier，整条流水线的
吞吐上限就等于一个人的检查速度，前面并行多少个 agent 都会堵在这里。

## 决策：补齐验证闭环的四层，顺序不可颠倒

**① 能力层**——agent 必须能自己运行产品、操作界面、读取运行时证据
（console / network / 性能轨迹 / 内存快照 / 移动端模拟器），而不是靠 `curl`
拿状态码去猜。没有这一层，后面三层都是空中楼阁。

**② 地图层（feature map）**——功能名 → 入口路由 → 关键组件 → 如何进入
（登录态/租户/前置步骤）→ 验证方式 → 已知坑。有了它，「一张截图」或
「某某页面坏了」这种模糊输入才能被机械地翻译成可复现的操作序列。
没有地图，agent 面对模糊描述只能 grep 猜，而猜测正是失败的主要来源。

**③ 技能层**——每一次发现 agent 在猜测、漏读代码、走错方向，就把这个
失败模式写成一条 skill。**失败模式不写成可执行的技能，就只是叙事**：
写在 ADR 与交接文档里的教训需要人读到、想起来、并且照做；写成 skill 才会
在下一次自动生效。

**④ 技能测试层**——skill 必须像代码一样被测试：多个 sub-agent 独立执行
同一批任务样本，coordinator 定 rubric，另一个模型交叉评分，迭代到结果稳定。
**没有测过的 skill 与没写过的 skill，在可靠性上没有区别**——这正是 ADR 0009
「门禁必须自证有效」在技能层的同构：一条从未被证明会失败的检查，等于没有检查。

四层齐备之后，自动合并才是安全的：agent 不是「因为 CI 绿了」而合并，
是「因为它自己操作过产品、拿到了证据」而合并。

## 前置条件：先有机械门，再谈自动化

实测本组织三个主力仓：`GET /branches/main/protection` 全部 404、`GET /rulesets`
全部返回空——**零机械门**。CI 红也能点 Merge，谁都能直推 main 触发生产部署。

**在这种仓上讨论「让 agent 自动合并」，等于在没有门的房子上装智能门锁。**
自动合并的前提是「CI 红不能合、不能直推 main」由平台强制，而不是靠自觉。
分档判定器因此内置前置检查：无保护即拒绝判档（退出码 30）。

另有三个已知弱点必须同时修，否则「CI 绿」这个信号本身不可信：
- PR 门禁里的 `npm run lint --if-present` 类写法，在缺脚本时**静默成功**——
  ADR 0009「跳过不是通过」的原样复现；
- 密钥扫描没有自证金丝雀，扫描器失灵与「干净」不可区分；
- PR 阶段构建的不是生产同形制品（生产走容器镜像），违反 ADR 0009 第三条。

## 一个不该自欺的观察

在单人仓里，「人工审查」和写代码的是同一个人。**自动合并真正省掉的是
等这个人按按钮，而不是替代第二双眼睛。** 承认这一点，才能把力气花在对的地方：
价值来自「让证据充分到不需要再看一眼」，而不是来自「跳过看一眼这个动作」。

## 后果

- 人的角色从 **verifier** 变成 **auditor**：不再逐个检查每次改动，而是抽查
  agent 提交的证据、以及审计每日自动合并摘要。
- 验证能力成为与 CI/CD 同级的基建：它需要版本化、需要守卫测试、需要在
  新仓接入时自动就位（与 ADR 0010 的对账循环同款思路）。
- 边界必须诚实：不是所有验证都能自动化。凡是**不可逆**或**需要外部凭据**
  的验证（真实支付、发送客户消息、数据迁移），永远留在人这一侧——
  自动化的是「确认功能是否成立」，不是「替人承担不可逆后果」。
