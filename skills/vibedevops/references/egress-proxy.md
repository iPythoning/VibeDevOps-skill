# 构建机出境代理方法论（工具无关）

> 本文是**方法论**，不绑定任何具体代理软件。凡涉及"本地代理"处，用占位符
> `PROXY_TOOL`（你的代理进程）、`PROXY_URL`（`http://127.0.0.1:PORT`，PORT 为其实际监听端口）、
> `SUB_URL`（订阅/节点来源）指代。示例命令用通用工具（`iptables`、`curl`、`systemd`），
> 不含任何厂商私有命令。

## 1. 为什么构建机要自建出境代理，而不是"等网络好"

受限或被 QoS 间歇整形的网络里，构建机到 CI 服务（GitHub 拉代码、拉基础镜像、
`git fetch` 全历史做 secret 扫描）的出境**时通时断**。"等网络恢复"不是工程方案：

- 断连发生在**无人值守的构建时刻**，job 直接红或挂死，等于没有 CI；
- 直连的通断是**外部变量**，你控制不了，但你能控制"断的时候有没有第二条路"。

根治思路：在构建机本地跑一个出境代理 `PROXY_TOOL`，把它当成**一条可随时启用的备用出境**。
配合网络自适应层（见 `net-adaptive.sh`）——直连通就直连、代理闲置，直连断就自动切代理——
路由变成**探测结果**而非写死配置。自建代理是"第二条路"的前提，自适应层是"自动选路"的开关。

## 2. 代理端口必须用网络层（iptables）收口，不能只靠应用层 allow-lan

几乎所有本地代理的混合端口（mixed-port 一类）**默认绑 `0.0.0.0`**，即监听所有网卡。
应用层的 `allow-lan: false` **不可靠**：不同工具语义不一，且一旦你为了容器接入把它打开
（见第 4 节），LAN/overlay 网络里的任何人都能借道你的代理出境——这是**开放代理**，是事故。

**正确做法：用 iptables 在网络层强制收口**，只放行明确需要的来源，其余一律 DROP：

```sh
# 只允许 本地回环 + docker 默认网桥网段 访问代理端口，其余全部拒绝。
PORT=<PROXY_PORT>
iptables -I INPUT 1 -p tcp --dport "$PORT" -j DROP
iptables -I INPUT 1 -p tcp --dport "$PORT" -s 127.0.0.0/8   -j ACCEPT
iptables -I INPUT 1 -p tcp --dport "$PORT" -s 172.17.0.0/16 -j ACCEPT   # docker0，按实际网段改
```

- **拒的是**：overlay/VPN 网卡（如 tailscale/wireguard）、物理 LAN 段——这些绝不该借道代理；
- **放的是**：`127.0.0.0/8`（宿主自身）+ **仅**你要放行的 docker 网段。

**让规则重启不丢**：把上述应用逻辑挂到代理服务的启动钩子（systemd `ExecStartPost`），
每次代理启动自动重放，避免"重启后 iptables 清空 = 悄悄变回开放代理"。写钩子时先幂等删除
同端口的旧规则再重加，防止重复插入越堆越多。

## 3. 容器里的 job 用不到宿主的 `127.0.0.1` 代理

CI 的构建步骤常在容器里跑。容器有自己的网络命名空间，容器内的 `127.0.0.1` 是**容器自己**，
不是宿主——所以容器 job **访问不到**宿主 `PROXY_URL`。两步打通：

1. **给容器一条到宿主的路**：运行容器时加
   `--add-host host.docker.internal:host-gateway`，容器内即可用
   `host.docker.internal:<PROXY_PORT>` 指向宿主网关上的代理；
2. **让代理接受容器来源**：容器来源 IP 属于 docker 网段（非回环），默认会被代理按
   "非本机"拒掉（表现为 **403**）。需在代理开 `allow-lan`（或等价的"接受非回环来源"），
   **同时**由第 2 节的 iptables 把来源死死限制在 docker 网段——两者配合，才是
   "容器能用（**200**）、LAN 不能用（被 DROP）"。开了 allow-lan 却不上 iptables = 开放代理。

一句话记忆：**host-gateway 解决"看得见"，allow-lan + iptables 解决"进得来但只放容器"**。
症状对照：不加 host-gateway = 连不上；加了但没开 allow-lan = 403；都对了 = 200。

## 4. 订阅/节点同步的"先有鸡后有蛋"

节点会过期、会变，需要定期从 `SUB_URL` 拉最新节点喂给构建机的 `PROXY_TOOL`。但这里有个死结：

> **构建机出境被封锁时，它自己拉不到 `SUB_URL`**——而恰恰是这时候它最需要新节点。

解法：**由一台"能出境"的机器代拉**（通常是你本地的常驻机），拉到后把节点文件推送给构建机、
热重载其 `PROXY_TOOL`。构建机永远是"接收方"，从不自己出境拉订阅。同步脚本挂在能出境的机器上
定时跑（如每 2 小时一次），只在节点**内容变化**时才推送 + 重载（对比 sha256），省事又留痕。

## 5. 解析校验：防"登录页/拦截页"污染节点文件

拉订阅时，若被中间设备劫持或订阅方要求重新登录，`SUB_URL` 返回的可能是一个 **HTML 登录页**
而非节点数据。若不校验就直接覆盖，会把构建机的可用节点冲成一堆垃圾，代理彻底失效。

**覆盖前必须解析校验**：把响应按预期格式（YAML/JSON）解析，确认**确实含有 ≥1 个节点**，
否则**保留构建机现有节点、拒绝覆盖**并记日志。宁可用旧节点，也不要用登录页覆盖。

```sh
# 伪代码：解析成功且节点数>0 才继续，否则退出不覆盖
count=$(parse_nodes "$downloaded_file")   # 解析失败/非预期格式 → 返回 0 或报错
[ "${count:-0}" -gt 0 ] || { log "订阅解析无有效节点（疑似登录页），不覆盖"; exit 0; }
```

## 6. 凭据只存 600 文件，不进 git / argv / 日志

`SUB_URL` 往往自带鉴权 token，是敏感凭据。硬红线：

- **存权限 600 的独立文件**（如 `~/.secrets/egress-sub.url`），运行时 `cat` 读取；
- **绝不写进命令行参数**（argv 会出现在 `ps`、shell 历史、CI 日志里）；
- **绝不 commit 进 git**（`.gitignore` 排除；只留 `.example` 占位）；
- **绝不打进日志**——日志里记"已同步 N 个节点"，不记 URL 本身。

同理，代理配置文件、节点文件也用 600，`scp` 到构建机后在对端再 `chmod 600` 一次。

- [ ] `SUB_URL` 等凭据存 600 文件，不进 argv/git/日志
