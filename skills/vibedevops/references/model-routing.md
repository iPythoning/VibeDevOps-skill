# 多模型 / 多 App 路由

## 默认角色

| 角色 | 默认模型 | 职责 |
|---|---|---|
| 主工程负责人 | Claude | 复杂需求、架构、跨模块主实现、风险判断与最终代码责任 |
| 视觉与交互审查 | Codex | 截图/页面验收、UI 修复、视觉回归与界面任务收口 |
| 高频执行员 | Reasonix + DeepSeek V4 Flash | 扫描、定位、小修复、测试分类和稳定会话中的低成本循环 |
| 架构挑战者 | Kimi | 长材料审阅、中文方案、独立反证和遗漏检查；默认只读 |

角色是默认路由，不是能力排名。没有视觉工作时跳过 Codex；低不确定性任务跳过 Kimi；简单任务只用一个模型。

## 复杂任务路由

1. 由 Claude 建立任务契约并承担主写入。
2. 将重复扫描、测试归类和小范围补漏交给 Reasonix/Flash。
3. 仅在高不确定性或长材料任务中让 Kimi 做独立反证。
4. 仅在 UI、截图、PDF 或视觉验收中让 Codex 介入。
5. 由当前主工程负责人吸收审查结论、运行完整验证并提交交接。

不要让多个模型同时修改同一工作树。并行任务必须使用不同 worktree、不同分支和互不重叠的写入范围。

## 接棒载荷

换 App 前在 `docs/HANDOFF.md` 写清：

- 当前写入者、App/模型、状态（写入中/待接棒/只读审查）。
- 分支、HEAD commit、工作树是否干净。
- 当前目标和可执行验收标准。
- 已完成内容及准确文件位置。
- 已运行命令、结果和失败证据。
- 未验证假设、风险和禁止事项。
- 下一棒及其唯一下一动作。
- UI 任务的截图或视觉验收点。

下一棒先读仓库规则与 HANDOFF，再核对 Git 状态和基线验证。HANDOFF 与 Git 不一致时，以 Git 事实为准，先修正交接状态再写代码。

## 缓存纪律

- Reasonix/Flash 的长期任务保持同一 provider、model、系统提示和工具清单。
- 不把其他 App 的完整聊天历史复制进 Reasonix；只追加结构化交接载荷。
- 架构切换、模型切换和工具表变化会形成新的缓存前缀，应放在明确的接棒边界。
